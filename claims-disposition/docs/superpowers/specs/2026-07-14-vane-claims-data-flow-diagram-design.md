# Vane 理赔多模态数据流程图设计

日期：2026-07-14  
状态：已确认

## 目标

在当前 Demo 项目中增加一张可编辑的 Excalidraw 数据流程图，用真实的车辆理赔处理链路说明 Vane 的价值：Vane 能把结构化数据、图片、文档、传统算法、OCR、AI 模型和确定性 SQL 规则组织成一条可验证、可治理并可发布的企业计算流水线。

主要读者是尚不了解 Vane 的跨行业企业潜在用户。图应让非技术读者在约 30 秒内理解价值，同时给技术读者留下足够的真实实现锚点。

## 核心信息

标题：

> 从多模态理赔证据到可信业务决策

副标题：

> Vane 将数据、算法、AI 与 SQL 规则统一在一条可验证流水线中

图要证明的核心观点是：

> 企业可以用 Vane 在同一计算图中处理多模态证据，以 AI 提取事实，以确定性规则控制决策，再把标准化结果可靠地交付给下游业务流程。

## 范围

图中包含：

- PostgreSQL 理赔单、MinIO 图片与文档、运行配置三类输入；
- Vane 内的数据接入、证据质量、OCR、图片计算、Qwen 推理、事实聚合和 SQL 决策；
- 证据不足、不确定或高风险、结论明确三类业务分流；
- `request_more_materials`、`manual_review`、`deny_claim`、`approve_for_payment` 四类输出；
- 输出契约校验、PostgreSQL 原子发布和结果验证；
- 从 Demo 中可以直接得到的 Vane 企业价值。

图中不展开：

- 每一条 SQL 判断条件和全部置信度阈值；
- 完整的九列字段清单；
- 每个 CTE、UDF 参数或 AI JSON Schema；
- 没有被当前项目直接证明的成本、性能或竞品对比结论。

这些细节保留在代码和 README 中，避免把产品叙事图变成规则手册。

画布使用横向布局、白色背景和清晰的左到右主路径。整体分为三个视觉层级：

2. 中部是主视觉，展示真实 Demo 从输入到决策发布的完整链路。Vane 计算区域是最大、最醒目的主体。

## 主流程设计

### 1. 多模态原始证据汇聚

左侧使用汇聚结构，而不是等宽卡片列表：

- PostgreSQL：理赔单与 `materials_json`；
- MinIO：JPEG 车辆照片；
- MinIO：PNG 理赔文档；
- `runtime.yml`：OCR、AI 与运行参数。

输入旁放置一段很小的真实 locator 样例，证明输入是可追溯的企业数据，而不是抽象图标：

```json
{
  "file_id": "PHOTO-APPROVE-001",
  "role": "damage_photo",
  "object_key": "claims/CLM-APPROVE/photos/PHOTO-APPROVE-001.jpg"
}
```

### 2. Vane 统一计算流水线

Vane 区域内部只保留四个易理解的阶段：

1. **数据接入**：将 PostgreSQL snapshot 和无凭据运行配置注册到同一个 DuckDB connection，并形成 SQL staging。
2. **证据质量**：校验材料定位、对象存在性与 SHA-256，执行照片质量计算、RapidOCR 和字段一致性检查。
3. **AI 事实提取**：仅对完整可用的输入调用 Qwen，多张照片分别生成结构化损伤事实，再进行聚合。
4. **SQL 决策**：用确定性业务规则把材料事实、AI 事实和风险信号转换为处置建议。

阶段下方使用小型技术标签保留真实实现锚点：

`DuckDB SQL`、`Vane UDF`、`RapidOCR Actor`、`vane.ai.prompt`、`Qwen2.5-VL`、`SHA-256`。

AI 阶段旁仅展示精简后的结构化事实样例：

```json
{
  "damage_visible": true,
  "severity_hint": "minor",
  "finding_determinate": true,
  "confidence": 0.90
}
```

样例用于说明数据形态，不表示 AI 直接作出处置决定。

### 3. 可信度与风险分流

详细规则压缩为三种业务语义：

- 证据不足 → 补充材料；
- 结果不确定或风险较高 → 人工复核；
- 结论明确 → 进入拒赔审核候选或支付流程候选。

随后以有优先级的扇出结构展示四种真实 disposition：

1. `request_more_materials`
2. `manual_review`
3. `deny_claim`
4. `approve_for_payment`

图中不罗列具体阈值、冲突条件和严重程度枚举，只用小注释说明“完整性、可信度、一致性与风险共同控制分流”。

### 4. 发布与验证

最右侧把工程交付压缩为一条短链路：

> 标准化九列输出 → 契约校验 → PostgreSQL 事务发布 → 结果验证

失败路径只保留两个关键语义：

- 输入不完整时跳过 AI，不让不可信输入产生自动结论；
- 发布失败时回滚，避免留下部分 snapshot。

使用四个 fixture 结果作为真实闭环证据：

- `CLM-APPROVE → approve_for_payment`
- `CLM-DENY → deny_claim`
- `CLM-MISSING → request_more_materials`
- `CLM-REVIEW → manual_review`

## Vane 价值总结

底部能力带只保留六项，并用细线连接到其证据来源：

- **多模态统一**：表格、JSON、图片、文档和模型响应进入同一计算图；
- **SQL 编排**：普通 DuckDB SQL 组织完整 DAG；
- **混合计算**：SQL、Python UDF、Stateful Actor 和多模态模型协作；
- **AI 可治理**：完整性门禁、结构化响应和风险分流约束 AI；
- **决策可信**：AI 提取事实，确定性规则负责最终分流；
- **生产可交付**：输出契约、事务发布、失败回滚和端到端验证。

收束语为：

> 可复用模式：多模态企业证据 → 可信事实 → 可执行决策

该表述帮助潜在用户把理赔案例映射到质检、合规、风控、运维和其他企业场景，但不在图中扩展额外行业流程。

## 视觉语言

遵循 Excalidraw 技能的统一配色：

- 主流程与 Vane 主体：蓝色；
- AI 计算：紫色；
- 输入触发：橙色；
- 成功输出与发布：绿色；
- 决策与分流：浅黄色；
- 拦截、异常与回滚：红色虚线；
- 证据样例：深色背景，绿色数据文本。

所有元素使用 `roughness: 0`、`opacity: 100` 和 `fontFamily: 3`。标题、注释和阶段说明尽量使用自由文本；只有输入、主要处理阶段、决策和输出等需要连接的实体使用容器。避免等宽卡片网格。

## 准确性与边界

- 图中所有技术名词、数据关系和输出均以当前项目代码为准。
- 图中明确标注输出是工作流处理建议，不是承保结论、责任认定、赔付金额计算或受监管的最终拒赔决定。
- 不展示真实客户数据、凭据、完整 DSN、API key 或 MinIO secret。
- AI 示例只说明结构化事实格式，不把模型输出描述为最终决策。

## 验证方式

完成图文件后执行以下检查：

1. JSON 能被 Excalidraw 和渲染脚本正常解析；
2. 渲染为 PNG 并进行完整视觉检查；
3. 修正文字裁切、元素重叠、箭头穿越、间距失衡和阅读顺序问题，重复“渲染—检查—修正”直到画面通过检查；
4. 对照 README、SQL DAG、fixture 和输出契约复核技术准确性；
5. 确认主流程在缩略视图下仍能读懂，细节不会压过 Vane 的价值主线；
6. 确认 `.excalidraw` 源文件和 PNG 预览均位于项目 `docs/` 目录。
